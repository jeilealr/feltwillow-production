# LUMI video-control results — 2026-10-16

**Decision: keep existing Wan I2V as the default. Keep Fun Control optional and
Blender experimental.** All three technical stages worked on LUMI, but this
pilot does not show an overall storytelling-quality gain from Blender/control.
The useful demonstrated gain is precise prescribed motion, with less spontaneous
acting. Blender did not improve on the cheap Python guide for this 2.5D task.

## Actual comparison

Pilot: Milo holding the acorn, `s01x_p03`, with `s01_p04` retained only as an
unused evaluation endpoint. Same fitted input bytes, prompt intent, 416×240,
33 frames at 16 FPS (2.0625 s encoded), seed policy 43. These are isolated
candidate experiments, not production-approved video pieces.

[Four-way video](../../work/stories/lion_and_mouse_v6/experiments/blender_fun_control/feasibility_20261016/comparison_4way.mp4)
shows normal Lightning I2V, plain I2V, Python Canny control and Blender Canny
control. Media are ignored local artifacts; retain the run directory when
sharing/backing up the experiment. All-frame contact sheets and individual
clips are alongside it.

| Method | Observed result | Practical assessment |
|---|---|---|
| Existing I2V + Lightning, 4 steps, guidance 1/1 | Recognizable feeding, blinking, head/body movement and acorn raised to mouth | Existing fast path remains a useful default for this shot |
| Existing plain I2V, 28 steps, guidance 3.5/3.5 | Richer feeding action, changes of gaze and posture; planted location and scene remain recognizable | More natural acting than the deliberately restrained guide examples; no clear need for Control here |
| Fun Control + Python Canny, 28 steps, guidance 6 | Small repeated head/acorn motion follows the guide; outline/camera stay near the starting pose | Useful precision, but mostly looks like an animated still; fixed face/background edges suppress spontaneous movement |
| Fun Control + Blender Canny, same settings | Similar prescribed motion and appearance to Python guide | Working end-to-end, with no demonstrated extra visual benefit from Blender |
| Same Control backend + stationary guide, same settings/seed | Nearly a hold | Moving-versus-static ablation demonstrates that the control input actually affects movement |

The guide deliberately asks for local image-plane movement, not an articulated
jaw or a walking animal. Its restrained acting is partly an authoring limitation,
not proof that Fun Control cannot animate naturally. Better acting requires
better guides/layers/poses; importing a still into Blender does not supply them.
Both regular and fast I2V make a more obvious feeding action in this example.
No automatic anatomy/identity approval follows from any of these observations.

All frame sequences were inspected through decoded-frame contact sheets and
peak-motion stills, with optical-flow diagnostics. This is agent analysis;
no owner visual-review ledger was filled. Full playback files are provided for
owner judgment. Pixel-flow magnitude is not an anatomical or quality score.
Different model weights, schedulers/guidance and CPU/CUDA generator implementations
mean equal seed numbers do not mean equal noise. The within-Control ablation
holds all other settings fixed and is the cleaner causal control test.

## LUMI and Blender feasibility

- Official sample inputs ran through the pinned Control backend on MI250X with
  bf16, PyTorch SDPA and model CPU offload. A tiny 9-frame/2-step diagnostic
  proved execution, not sample quality.
- The story control clips decoded/exported all 33 frames. Peak allocated HBM
  was about **28 GiB**, with about **69 GiB process RSS**, on one 64 GiB GCD.
  Jobs requested 128 GB host RAM. Native 720p/81-frame resource use is untested.
- Blender **4.5.0** works headlessly through its official bpy wheel. Cycles CPU
  rendered all 33 textured image-plane frames in **7.0 s**, about **50 s** for
  the allocated CPU step including startup. No OpenGL, Vulkan, EEVEE or MI250X
  graphics rendering was used. The actual CPU step used one core.
- Blender's first frame had RGB mean absolute error **0.165/255** against the
  fitted source, demonstrating image-space alignment. The actual Blender frames
  were converted with Canny 100/200 and consumed successfully by Wan.
- This proves a **2.5D image-plane mesh**, not a calibrated 3D stage, animal rig,
  quadruped gait, depth-control backend, collision/contact solver or camera rig.

## Cost and baseline loading improvement

Approximate single-run Python elapsed time, including startup/loading:

| Run | Elapsed | Notes |
|---|---:|---|
| Python control + stationary ablation | 11.4 min | Two clips share one model load; stationary ablation adds 2.2 min |
| Blender-conditioned control | 9.5 min | One clip; guide rendering is a small part of total cost |
| Plain I2V | 8.4 min | Video complete; preview-only failure recovered on CPU |
| Normal Lightning I2V | 7.8 min | Four steps; cold setup/transfers dominate this short clip |

These are single observations on different allocated nodes, not a controlled
throughput benchmark. Do not extrapolate a native production speedup from them.
Control training/LoRA compatibility beyond these configurations is untested.

The original baseline FP32 load was cancelled before inference when shard
loading exceeded the short-test budget. A separate cache writer then passed
its first bounded CPU diagnostic in **2m39s**, verifying every saved tensor
byte-for-byte against the baseline's ordinary bf16 cast: **2,190 tensors,
24 shards**. It adds 57.16 GB of expert storage; originals are retained and
VAE/text-encoder files are unchanged. This is the same inference precision
already used by `feltwillow/wan.py`, not an additional FP8 approximation.

Both actual baseline renders used this verified local cache through the existing
`wan.load`/`wan.generate` API. Production module files and default model selection
were unchanged; the path override exists only inside the experiment process.
Loading pipeline components took ~53 s for plain I2V, versus minutes per FP32
shard in the abandoned attempt. Storage precision, conversion overhead and node
I/O are confounders: this is not evidence that Control itself is faster.
The verified cache is a useful optional loading optimization independent of Blender.

A NumPy-versus-PIL preview error occurred after plain I2V's MP4 was exported.
The raw failed receipt is preserved. CPU recovery checked 33 decoded frames,
dimensions/FPS and output SHA, then saved previews in a separate recovery receipt.
No GPU inference was repeated to repair previews. Future preview handling accepts
both frame types. Production MP4 export already accepted the NumPy frames.

## Go / no-go and next boundaries

| Decision | Result |
|---|---|
| Can this Control stack execute on LUMI ROCm? | **GO**, at the tested resolution/duration/precision |
| Can a cheap guide influence a felt mouse's motion? | **GO**, demonstrated by the stationary/moving ablation |
| Can Blender render a compatible guide without graphics GPUs? | **GO**, CPU Cycles plus Canny proved end-to-end |
| Should Blender become required for video creation now? | **NO-GO**; no gain over Python for this task |
| Should Control replace existing I2V now? | **NO-GO**; no clear overall quality gain on this pilot |
| Could Control help a shot requiring exact blocking/cadence? | Worth an opt-in experiment when I2V has a specific observed failure |

Before any production adoption, validate native resolution/duration, required
end-image anchoring, animal walking/contact and harder interactions, and review
actual output benefit against the existing fast/plain options. These remain
untested. V6 runtime/keyframe/timing approvals remain authoritative and blocked;
none was bypassed or edited. Agent A's image-generation/staging policies are untouched.

All GPU work here was bounded initial diagnostics, one running GPU test at a
time. CPU cache validation had a 15-minute cap and an automatic ten-minute
projection gate. Regular small/small-g jobs were queued as appropriate but
cancelled when no longer needed. No routine production batch ran in debug/dev-g.
Temporary files now use job-specific subdirectories under
`/scratch/project_465002727/jelealro/tmp`, including container temporary settings.
For routine future runs, use the regular partitions in the experiment policy.
